**[Documentation](https://ctolon.github.io/gormgate/)** ·

gormgate is a port of Django 6.0's migration framework: the autodetector,
the migration graph, the optimizer, the executor, the squash machinery and
the management commands. Given the same models it writes the same
migrations, with the same operations, in the same order, and returns the
same exit codes. Migrations are Go files, generated and compiled into your
own `gorm-gate` command.

```
$ go run ./cmd/gorm-gate makemigrations blog
created blog/migrations/0002_post_views.go
  + add field views to post

$ go run ./cmd/gorm-gate migrate
applying blog.0002_post_views ... ok
```

## Setup

Declare the apps and databases in your own gorm-gate command:

```go
package main

import (
	"context"
	"os"

	"gorm.io/driver/postgres"
	"gorm.io/gorm"

	"example.com/blogproj/auth"
	"example.com/blogproj/blog"
	"github.com/ctolon/gormgate"
	_ "github.com/ctolon/gormgate/backends/postgresql" // the backend(s) you use
)

func main() {
	gormgate.Execute(&gormgate.Settings{
		Apps: []*gormgate.AppConfig{
			gormgate.App("auth", &auth.User{}),
			gormgate.App("blog", &blog.Post{}, &blog.Comment{}),
		},
		Databases: map[string]gormgate.Database{
			"default": {Open: func(ctx context.Context) (*gorm.DB, error) {
				return gorm.Open(postgres.Open(os.Getenv("DSN")))
			}},
		},
	})
}
```

`makemigrations` writes `<app>/migrations/0001_initial.go`, a
`migrations.go` that registers the package, and
`cmd/gorm-gate/zz_gormgate_migrations.go` which imports every migrations
package — so the next `go run ./cmd/gorm-gate` compiles the new migration in.
Nothing has to be wired by hand.

A generated migration is ordinary Go — this is the file the run above
wrote, unedited:

```go
// Generated by gormgate 0.1.0 on 2026-09-23 07:07

package migrations

import (
	m "github.com/ctolon/gormgate/migrations"
)

func init() {
	m.Register(&m.Migration{
		App:  "blog",
		Name: "0002_post_views",
		Dependencies: []m.Key{
			{App: "blog", Name: "0001_initial"},
		},
		Operations: []m.Operation{
			&m.AddField{
				ModelName: "post",
				Name:      "views",
				Field: m.Field{
					Type:      m.Int,
					Size:      64,
					DBDefault: m.DBValue(int64(0)),
				},
			},
		},
	})
}
```

## Commands

The commands are Django's, and so are the decisions they take and the exit
codes they return. The options are spelled the way Go command line tools
spell them; [`docs/from-django.md`](docs/from-django.md) has the mapping.

| Command | |
| --- | --- |
| `makemigrations [app_label …]` | `--dry-run --merge --empty -y/--no-input -n/--name --no-header --check --scriptable --update` |
| `migrate [app_label] [migration_name\|zero]` | `--database --fake --fake-initial --plan --run-syncdb -y/--no-input --check --prune` |
| `sqlmigrate app_label migration_name` | `--backwards --database` |
| `showmigrations [app_label …]` | `-p/--plan --database` |
| `squashmigrations app_label [start] migration_name` | `--no-optimize -y/--no-input --squashed-name --no-header` |
| `optimizemigration app_label migration_name` | `--check` |
| `sqlsequencereset app_label …` | `--database` |
| `inspectdb [table …]` | `--database --include-partitions --include-views` (outputs gorm structs) |
| `check [app_label …]` | `-t/--tag --list-tags --deploy --fail-level --database` |

Global options: `-q -v/-vv --settings --no-color --force-color
--skip-checks`, plus `help`, `help <subcommand>`, `completion` and
`version`.

Data migrations use `RunGo`, the equivalent of Django's `RunPython`. Its
function is given the models **as they were at that point in the history**,
never today's structs, so it still works when the migration is replayed on
a fresh database years later:

```go
func resetViews(apps *m.Apps, ed m.SchemaEditor) error {
	post, err := apps.GetModel("blog", "post")
	if err != nil {
		return err
	}
	_, err = post.Objects(ed).UpdateAll(map[string]any{"views": 0})
	return err
}

// in the migration's Operations:
&m.RunGo{Code: resetViews, ReverseCode: m.RunGoNoop}
```

It has to be a package-level function: a closure cannot be written back
into generated source, and gormgate says so rather than guessing.

PostgreSQL's own operations — extensions, concurrent indexes, collations,
`NOT VALID` constraints — are ported as
[`migrations/postgres`](https://pkg.go.dev/github.com/ctolon/gormgate/migrations/postgres),
the counterpart of `django.contrib.postgres.operations`.

## Databases

Every backend is verified against a real server: the operation conformance
suite applies each operation forwards, compares the schema with one built
from scratch, unapplies it, re-applies it and replays the SQL that
`sqlmigrate` collects — and a gorm-parity suite requires the schema
gormgate creates to be identical to the one `AutoMigrate` creates.

| Backend | Import |
| --- | --- |
| PostgreSQL | `backends/postgresql` |
| CockroachDB | `backends/cockroachdb` |
| GaussDB / openGauss | `backends/gaussdb` |
| MySQL, MariaDB | `backends/mysql` |
| TiDB | `backends/tidb` |
| SQLite | `backends/sqlite3` |
| SQL Server | `backends/mssql` |
| Oracle | `backends/oracle` |
| ClickHouse (documented subset) | `backends/clickhouse` |

See `docs/vendors.md` for per-database behaviour and limitations.

## Why it decides what Django decides

`itest/parity_test.go` runs the same command sequences against a real
Django 6.0 project (Python 3.14, in Docker) and an equivalent gormgate
project, and requires the two to agree on what they did: the same exit
status, the same migrations written, and the same migrations and
operations planned, in the same order.

`docs/deviations.md` lists the few places where gormgate deliberately
decides differently, because gorm models work differently.

## Tests

```console
$ make test                      # unit tests, no database
$ make lint                      # gofmt, go vet, staticcheck, docs drift
$ make itest-up                  # start every database service
$ make integration VENDOR=pg18   # conformance and gorm parity on one vendor
$ make parity                    # run the same scenarios against Django 6.0
```

`make help` lists the rest. Oracle needs Oracle Instant Client and so runs
in a container: `make -C itest oracle-test`.

## Examples

Five runnable projects under [`examples/`](examples/), each its own module
with a README whose output was captured from a real run:
[blogproj](examples/blogproj/) (the smallest complete project),
[dockerproj](examples/dockerproj/) (migrations as a deploy step, with
Compose), [datamigration](examples/datamigration/) (backfilling a new
`NOT NULL` column), [multidb](examples/multidb/) (two databases and a
router) and [adoptdb](examples/adoptdb/) (taking over a database gormgate
did not create).
