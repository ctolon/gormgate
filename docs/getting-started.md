# Getting started

This walks through a project from nothing to an applied migration. It
follows `examples/blogproj` in the repository, which is the same project the
end-to-end test suite drives.

## Install

```console
$ go get github.com/ctolon/gormgate
```

You also need a gorm driver for your database, and gormgate's backend for
it. Backends register themselves, so a blank import is enough:

```go
import (
	"gorm.io/driver/postgres"

	_ "github.com/ctolon/gormgate/backends/postgresql"
)
```

The driver lives in your module, not in gormgate's, so adding gormgate does
not pull ten database drivers into your build. Its own dependencies are
`gorm.io/gorm` and cobra.

## The models

Ordinary gorm models. Nothing about them is gormgate-specific:

```go
// blog/models.go
package blog

import (
	"time"

	"example.com/blogproj/auth"
)

// Post is a blog post.
type Post struct {
	ID        uint      `gorm:"primaryKey"`
	Title     string    `gorm:"size:200;not null"`
	Body      string    `gorm:"type:text"`
	AuthorID  uint      `gorm:"not null"`
	Author    auth.User `gorm:"constraint:OnDelete:CASCADE"`
	CreatedAt time.Time
}
```

## The command

Your project gets its own command. This is what `makemigrations` and
`migrate` are run through, and it is the file that declares which apps and
databases exist:

```go
// cmd/gorm-gate/main.go
package main

import (
	"context"
	"fmt"
	"os"

	"gorm.io/driver/postgres"
	"gorm.io/gorm"

	"example.com/blogproj/auth"
	"example.com/blogproj/blog"
	"github.com/ctolon/gormgate"
	_ "github.com/ctolon/gormgate/backends/postgresql"
)

func main() {
	gormgate.Execute(&gormgate.Settings{
		Apps: []*gormgate.AppConfig{
			gormgate.App("auth", &auth.User{}),
			gormgate.App("blog", &blog.Post{}, &blog.Comment{}),
		},
		Databases: map[string]gormgate.Database{
			"default": {Open: func(ctx context.Context) (*gorm.DB, error) {
				dsn := os.Getenv("BLOGPROJ_DSN")
				if dsn == "" {
					return nil, fmt.Errorf("BLOGPROJ_DSN is not set")
				}
				return gorm.Open(postgres.Open(dsn))
			}},
		},
	})
}
```

An *app* is a named group of models, like a Django app. The label is what
appears in migration paths, command output and dependencies between apps.

!!! note "Apps are declared, not discovered"
    Go has no runtime import, so gormgate cannot find your models by
    scanning. Listing them here is also what lets `makemigrations` work with
    no database connection at all.

## The first migrations

Name the apps the first time. Like Django, the bare form only considers apps
that already have a migrations package, so on a fresh project it finds
nothing:

```console
$ go run ./cmd/gorm-gate makemigrations
no changes detected

$ go run ./cmd/gorm-gate makemigrations auth blog
created auth/migrations/0001_initial.go
  + create model User
created blog/migrations/0001_initial.go
  + create model Post
  + create model Comment
```

Three kinds of file were written:

```
auth/migrations/0001_initial.go        the migration
auth/migrations/migrations.go          registers the package
cmd/gorm-gate/zz_gormgate_migrations.go  imports every migrations package
```

The last one is why the next `go run` already knows about what you just
generated.

## Look before you leap

```console
$ go run ./cmd/gorm-gate sqlmigrate blog 0001
BEGIN;
--
-- create model Post
--
CREATE TABLE "blog_posts" ("id" bigserial, "title" varchar(200) NOT NULL, "body" text, "created_at" timestamptz, "author_id" bigint NOT NULL, PRIMARY KEY ("id"));
...
COMMIT;
```

That is the same DDL `gorm.AutoMigrate` would emit for these models — which
is what makes adopting an existing database possible.

## Apply them

```console
$ go run ./cmd/gorm-gate migrate
applying auth.0001_initial ... ok
applying blog.0001_initial ... ok
```

```console
$ go run ./cmd/gorm-gate showmigrations
auth
 [X] 0001_initial
blog
 [X] 0001_initial
```

## Change a model

Add a field:

```go
	Views     int       `gorm:"not null;default:0"`
```

```console
$ go run ./cmd/gorm-gate makemigrations
created blog/migrations/0002_post_views.go
  + add field views to post
```

and the file it wrote:

```go
// Generated by gormgate 0.1.0 on 2026-09-23 07:07

package migrations

import (
	m "github.com/ctolon/gormgate/migrations"
)

func init() {
	m.Register(&m.Migration{
		App:  "blog",
		Name: "0002_post_views",
		Dependencies: []m.Key{
			{App: "blog", Name: "0001_initial"},
		},
		Operations: []m.Operation{
			&m.AddField{
				ModelName: "post",
				Name:      "views",
				Field: m.Field{
					Type:      m.Int,
					Size:      64,
					DBDefault: m.DBValue(int64(0)),
				},
			},
		},
	})
}
```

It is ordinary Go. You can read it in review, edit it, and add operations to
it by hand — see [Writing migrations](guide/writing-migrations.md).

```console
$ go run ./cmd/gorm-gate migrate
applying blog.0002_post_views ... ok
```

## In continuous integration

Two checks are worth adding:

```console
$ go run ./cmd/gorm-gate makemigrations --check --dry-run   # a model changed without a migration
$ go run ./cmd/gorm-gate migrate --check                    # the database is behind
```

Both exit non-zero rather than doing anything.
